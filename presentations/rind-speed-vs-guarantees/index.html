What constant time needs from the CPU · kixel-ai/rind#821

Intel's list of fixed-timing instructions has the SHA-1 and SHA-256 ones, and none of the SHA-512 ones

Intel "Data Operand Independent Timing Instructions", page updated 2026-02-23
InstructionOn the list
SHA1RNDS4, SHA1MSG1/2, SHA1NEXTEyes
SHA256RNDS2, SHA256MSG1/2yes
VSHA512RNDS2, VSHA512MSG1, VSHA512MSG2no

Why it matters

  • rind ran the VSHA512 instructions on every x86_64 CPU with the SHA512 extension, from Arrow Lake and Lunar Lake on.
  • So HMAC keys and Ed25519 nonces went through instructions with no timing guarantee.
  • admin/ct-vartime, the tool meant to catch that, accepted them.

What rind did · kixel-ai/rind#821 · merged 19 Nov, 2:48 PM

No VSHA512 on x86_64: those CPUs take OpenSSL's AVX2 routine, which already has rind's proof

code
  • SHA-384, SHA-512 and SHA-512/256 use the AVX2 routine, as aws-lc does.
  • Every mnemonic in it is on Intel's list.
  • No API or wire change; digests unchanged.
checks
  • admin/ct-vartime now refuses vsha512* on x86.
  • HMAC-SHA384 and HMAC-SHA512 now run only what valgrind models, so ctgrind covers them.
proofs
  • The AVX2 routine has rind's HOL Light proof, so x86_64 SHA-512 is proven on every AVX2 CPU.
  • The proof quest for the removed routine is retired.

The OS can hide a CPU feature: /proc/cpuinfo does not list sha512, but the chip has it

CheckWhat it shows
OSOracle Linux Server 10.2

CPUIntel Core Ultra 9 275HX

rind's runtime CPUID detection, 13 Nov runsha512 found
#821 commit a674bc6e on this chip2.0× to 2.2× (32 and 64 B) and 4.4× to 4.7× (from 1200 B) slower after the change

Why the slowdown settles it

  • #821 only changes CPUs that take the SHA512 path. A chip without it would have run the AVX2 routine before and after, with no slowdown.
  • This chip slowed down by 2× to 4.7×, so the SHA512 path was in use.
  • Why the kernel does not list the flag here is not checked; this slide only says it is not listed.
Takeaway: trust CPUID detection over /proc/cpuinfo, and record both in every results run.

What the fork tried, and one more guarantee

Keeping VSHA512 for public inputs only was measured and dropped; a fork-safe self-test costs one run

fork #131, merged on the fork

  • The fork's mirror of #821, with review fixes. Merged into fork main 19 Nov, 7:47 AM.
  • It keeps the sha512-x86-ext quest as a revisit quest; upstream deleted it.

fork #136, closed

  • Would have kept VSHA512 for Ed25519 verification only.
  • Measured verify gain within noise: 1.8% slower on a CPU without VSHA512, 0.5% to 1.8% at best with it.

#723, merged 14 Nov

  • The FIPS DRBG self-test could hang a forked child. A per-thread test was about 9.6 µs per thread against about 19.6 µs to spawn one.
  • The shipped once-per-process flag costs one run. Maintainer's timing.
