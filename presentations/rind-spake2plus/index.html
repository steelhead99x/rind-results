The problem

A client should prove it knows a password without sending it, and a stolen server database should not let anyone pose as the client

Requirement 1: the password never crosses the wire

  • Client and server share a password, or a value derived from it.
  • They agree on a session key, and each proves to the other that it knows the password.
  • Someone who records the exchange cannot test password guesses offline.

Requirement 2: the server record is not a password

  • Servers get breached. Whatever the server stores should not be enough to log in as the client.
  • The attacker who steals the record can still run a guessing attack against it, but cannot use the record itself as a credential.
  • SPAKE2+ (RFC 9383) meets both. Matter uses it for PASE, its commissioning handshake.
RFC 9383 · draft-bar-cfrg-spake2plus-01 · moq-dev/rind#689
The protocol on one page

Both sides exchange masked shares, derive the same keys, and trust the key only after the tags check

RFC 9383, section 3 · M and N are fixed curve points; G is the generator
Step 1 · setup

The verifier stores w0 and L = w1·G, so a stolen record cannot act as the client

This is the "+" over SPAKE2: the two sides hold different secrets.

Password to w0, w1

  • The caller stretches the password with a slow hash and derives two scalars, w0 and w1.
  • rind takes w0 and w1 as input. Choosing the stretching function is the caller's job.

Who holds what

  • Prover (client): w0 and w1.
  • Verifier (server): w0 and L = w1·G, computed once at registration.

Why L is safe to store

  • Recovering w1 from L is a discrete-log problem on P-256.
  • The prover's V uses w1 directly. Without w1, a thief holding (w0, L) cannot compute the prover's V, so the tags fail.
RFC 9383, sections 3.2 and 3.3
Step 2 · masked shares

Each share is masked with w0, so an eavesdropper cannot test password guesses offline

X = x·G + w0·M (prover)
Y = y·G + w0·N (verifier)
  • x and y are fresh random scalars for each handshake.
  • M and N are fixed points whose discrete logs nobody knows.
  • A guessed w0 turns a recorded X into a candidate x·G, but checking it means computing Z, which needs x or y. Neither leaves its owner.

What an attacker can do

  • Passive: record X and Y. They look like random points, and give no way to check a guess.
  • Active: run the handshake with one guessed password. A wrong guess fails at the tag check.
  • So each attempt tests one guess, online. The guesses cannot be run offline.
RFC 9383, sections 3.3 and 4 (M, N for P-256 are given in the RFC)
Steps 3 to 6 · compute and confirm

Both sides reach the same Z and V, hash the transcript into keys, and release the key only after the peer's tag checks

Same values, different inputs

  • Prover removes w0·N from Y, then multiplies by x and by w1.
  • Verifier removes w0·M from X, then multiplies by y; it gets V from L as y·L.
  • Both end with Z = xy·G and V = w1·y·G.

Transcript into keys

  • The transcript is context, both identities, M, N, X, Y, Z, V and w0.
  • It is hashed into two confirmation keys and the shared key.
  • Any change to any field gives different keys, so a tampered handshake fails at the tags.
Confirmation tags are compared in constant time. rind returns the shared key only after the peer's tag checks. A failed handshake tells an active attacker that one guess was wrong, and nothing else.
RFC 9383, sections 3.4 and 3.5 · moq-dev/rind#689
rind design · two suites

rind ships two suites, RFC 9383 and Matter PASE, and the type system keeps them from being mixed

Suite<Rfc9383>Suite<MatterPase>
SpecRFC 9383draft-bar-cfrg-spake2plus-01, which Matter PASE uses
Key scheduleTranscript hash fed to HKDFHash(TT) split into Ka || Ke; confirmation keys come from HKDF over Ka; 16-byte keys
PrimitivesP-256, SHA-256, HKDF-SHA256, HMAC-SHA256. All already in rind; no new primitive.
The draft disagrees with itself. Its prose and its diagram split Hash(TT) differently. rind follows the draft's appendix B test vectors and the connectedhomeip vectors.
The suite is part of the type. Mixing the two suites in one handshake fails to compile.

rind design · the hard part

The identity check runs without a secret-dependent branch

A share equal to w0·M or w0·N makes X − w0·M or Y − w0·N the identity point, and the handshake must reject it. Testing for that with an ordinary if would branch on a value derived from the password.

How rind does it

  • If the point is the identity, the multiplication and the transcript run on the generator instead, so the work looks the same either way.
  • The "was identity" bit is declassified once, together with the tag check result.
  • The maintainer refactored complete_add onto hash-to-curve's sum.

Other limits and hygiene

  • Hostile input is bounded: context and identities at 1024 bytes, scalars at 128 bytes.
  • Secrets are wiped on drop.
  • Per-handshake state is consumed by finish, so it cannot be reused.
  • One stored record (or one set of prover secrets) serves many handshakes.

On the Pi 5, rind now matches or beats aws-lc-rs on the ops shown, and its Argon2id beats RustCrypto

Raspberry Pi 5 (Cortex-A76) for public-key ops and Argon2id; Apple M1 Pro for the first Argon2id NEON work.

Raspberry Pi 5

  • PR #33 picks narrow multipliers on the A76: X25519 0.43× the wide path.
  • Follow-ups: ECDSA verify now 0.75× (P-256) and 0.73× (P-384, P-521) of aws-lc-rs; RSA-3072/4096 verify 0.87× / 0.88×.
  • Argon2id: 29–39% less time than RustCrypto across 1, 16 and 64 MiB.

Apple M1 Pro

  • Argon2id NEON fill, 1 MiB t=3: 1.106 → 0.724 ms, against 1.054 ms for RustCrypto.
  • SHA3 umlal BlaMka: 0.865× at 1 MiB.
