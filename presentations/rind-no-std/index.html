Why no_std

A crate that promises its users no_std cannot offer rind as a backend today

Decided 2026-11-12 by the maintainer in a quest audit: a no_std build is one of the four ecosystem bets.

The goal, from the quest

  • The rind crate is #![no_std] with alloc.
  • CI builds it for a target that has no std.
  • Then an embedded or kernel project, and any crate that is itself no_std, can depend on it.
  • Nothing changes for a caller on a hosted target.

Who it is for, and what stays on std

  • RustCrypto's crates and ring are no_std. A crate that promises no_std can pick them as a backend, but not rind, however the rest fits.
  • The adapters stay on std, because their upstreams' providers are.
  • Once CI builds a no_std target, the README's "Maturity and reach" bullet drops its std sentence.
  • Microcontrollers: the board runs on slide 8 already need no_std, and get it today from out-of-tree patches.

The approach in #84

On target_os = "none" the crate is no_std on alloc; every hosted target is unchanged

rind/src/lib.rs

One cfg, no feature

  • #![cfg_attr(target_os = "none", no_std)] and extern crate alloc there.
  • No std feature, as the quest recommends. UEFI and other target_os values are out of scope.
  • The program supplies a global allocator and a getrandom backend.
  • --cfg rind_fips stops at a compile_error: the FIPS module needs std.
rind/build.rs

Backend choice

  • Bare-metal aarch64 and 32-bit ARM, and every M-profile triple, get the portable backend.
  • Reason: that assembly does unaligned loads and stores (AES-GCM's ldp), and aarch64-unknown-none and armv7a-none-eabi are strict-align targets.
  • x86_64 keeps its backend only when the target enables SSE2 (slide 5).
low/cpu.rs · low/entry.rs · reuse cache

Shared state

  • The DIT guard and the debug Entry count stay thread-local when hosted, and do nothing on bare metal.
  • Sound there because the only bare-metal backends, portable and x86_64, set no CPU state.
  • Without target_has_atomic = "8" the reuse cache keeps nothing; each use builds the value.
  • SHA-1/256/512 pick their path per call instead of via OnceLock.
No public API or wire change. MD5's empty asm! barrier is allow-listed to architectures whose reg operand is stable; Xtensa, wasm, Miri and the rest use black_box.

x86_64-unknown-none

Bare-metal x86_64 is the one target that keeps assembly, and only when the caller opts in

Default build: portable

  • x86_64-unknown-none is soft-float and does not enable SSE2, so it stays on the portable backend.
  • It must set --cfg curve25519_dalek_backend="serial" or "fiat": dalek's default simd backend does not compile there. A compile_error says so.
  • The portable backend leaves out stmxcsr, which raises #UD when CR4.OSFXSR is clear. The lint disassembles the rlib and fails on stmxcsr.

Opt-in: -C target-feature=+sse,+sse2,-soft-float

  • Selects the x86_64 backend, which reads CPUID.
  • AVX, AVX2, SHA512, VAES, VPCLMULQDQ and AVX-512 run only when those target features are enabled. XCR0 is not treated as proof that an interrupt saves YMM or ZMM.
  • SSE2 alone leaves soft-float set and LLVM aborts. Clearing soft-float this way is slated to become an error (rust-lang/rust#116344); the workaround is in UPSTREAM.md.
Differs from the quest. The quest says bare-metal x86_64 checks OSXSAVE and XCR0 before it picks an AVX tier. #84 uses compile-time target features instead, and lists this as an open decision for the maintainer.

What sh/bare-metal.sh checks

  • cargo clippy -p rind --lib -D warnings per target, dev and release; getrandom's custom backend stands in.
  • A build of x86_64-unknown-none with SSE2.
  • The same target without SSE2 and with dalek serial; its rlib is disassembled and rejected if it emits stmxcsr.
  • The bench crate has no aws-lc dependency for thumbv7em-none-eabihf.
  • Runs as just bare-metal and in just check's cross module when a change reaches x86_64, aarch64, arm or portable.
Lint and build only: nothing links a program, runs a test, or checks constant time on these targets.

How it was run, and its limits

  • Ryzen 5 7535HS host, which the PR calls not quiet; criterion, 3 s measurement, pinned to core 2, five alternating rounds.
  • The table ran at ea548396. The per-call SHA path pick (no OnceLock) came after e93a3c1a and was measured on its own: a 2-core cloud VM (SHA-NI, AVX2), six rows, −3.3% to +3.1%, inside each run's spread. That test has no aws-lc-rs rows.
  • The PR asks for a quiet rerun on a dedicated host.

Open questions and next steps

One decision for the maintainer, a no-CAS cache to design, and the upstream port

Open

  • AVX tier on bare-metal x86_64: OSXSAVE/XCR0 as the quest says, or compile-time target features as #84 does.
  • Reuse cache without CAS (quest/m2/no-cas-reuse-cache.md): atomic words plus a ready flag, returned by copy; whether by-copy get_or_build applies on every target; whether ML-DSA's boxed matrix may leak one build per race.
  • No assembly on bare-metal aarch64 and arm: keeping it would need every kernel's loads audited for strict alignment.
  • -soft-float is slated to become a hard error (rust-lang/rust#116344).

Next

  • Resolve the conflicts with fork main; GitHub marks #84 conflicting.
  • Quiet rerun of the SHA-256 64 B and AES-GCM 128 B rows against aws-lc-rs on a dedicated host, at the current head: the per-call path pick has no aws-lc-rs comparison yet.
  • On port: delete the upstream quest and the README's std sentence; reconcile with kixel-ai/rind#696, which also removes the runtime CPU check.
  • #85 (ESP32 Xtensa lint) is stacked on #84.
  • Board timing on #84's code path; the RP2040 still has no published timing tree. thumbv8m.main (MG24) is not in the lint list.
Not run for #84: just ci (needs the nix toolchain) and anything on bare-metal hardware.
