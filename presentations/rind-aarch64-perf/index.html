Executive summary

On the Pi 5, rind now matches or beats the reference libraries in most measured operations

The cause was the same on both tracks: code tuned for Apple's wide cores was running on the A76. PR #33 changed the dispatch, and the Argon2 fill now overlaps its dependency chains. The Nov 11–12 results are on rind-results main. The code is not on rind main yet: PR #33 was closed unmerged on Nov 12, and on Nov 13 draft PR #82 re-proposed the dispatch on current main and reproduced its gains.

  • Public key: PR #33's narrow schedules take 10–57% off every one of the 16 report operations on the A76 (narrow/wide 0.43–0.90). A full suite of stock upstream main on Nov 13 confirms the starting point: rind leads on 45 of 68 operations, and every remaining gap is in public-key code.
  • Follow-ups: the narrow NIST routines and the width-7 NAF branches put ECDSA verify at 0.73–0.75× aws-lc-rs, and rsa-8n puts RSA-3072 sign at 0.96×. A 2.5–3.1% P-256 loss in the cpu-detect build was traced to where the linker put a table; aligning it to 64 bytes removes it.
  • Argon2id: the NEON fill (M1) beats RustCrypto. umlal is 13% faster on the M1 but 2.5% slower on the A76, so it is gated to SHA3. The two-round interleave plus scalar riders bring the Pi 5 fill to 0.55–0.68× its original time.
  • Correctness: lib and crosscheck tests pass on both machines, and ct-vartime passes. The ct-qemu, ctgrind and BINSEC aarch64 checks are green, and each remaining failure is a tool or test issue with a patch ready.

Where we started · 2026-11-11

At the start, rind trailed aws-lc-rs and RustCrypto on the Cortex-A76

rind already led on Apple M-series, and the same code was behind on the Pi 5.

Public key: wide code on a narrow core

  • Fork main ran s2n-bignum's _alt routines on every aarch64 core. They are tuned for cores with a fast high multiply (umulh).
  • Pi 5 gaps to aws-lc-rs at b6651423 (hosts/pi5/NOTES.md): X25519 2.32×, RSA-2048 ≈1.65×, P-curve ECDH 1.5–1.6×, Ed25519 ≈1.45×.
  • PR #33 (cursor/aarch64-narrow-mul-132a) selected the non-_alt schedules on A72/A76/N1. Its results table said "not measured".
  • The box scout's llvm-mca run (Neoverse N1 model) predicted a 2.35× alt/narrow X25519 ladder ratio, against the 2.32× seen on the Pi.

Argon2id: a new NEON fill that still lost on the A76

  • On the M1 Pro the first NEON permutation was slower than RustCrypto's portable code: it went through memory three times per 1 KiB block (bd907631).
  • By the end of 2026-11-11 the branch (perf/argon2-neon @ 4ad61ae3) led on the M1. The SHA3 fill took 0.724 ms at 1 MiB, against 1.054 ms for RustCrypto.
  • On the Pi 5 the same branch took 4.729 ms vs RustCrypto's 4.201 ms at 1 MiB, t=3 (measured 2026-11-12). RustCrypto's scalar fill beat every rind fill by about 12%.

Hardware and method

Each comparison is an interleaved A/B run on one quiet core, under a shared lock

Other agents shared both machines, so every timed run took a lock, logged the load, and kept a control library in the same binary.

Raspberry Pi 5

  • BCM2712, 4× Cortex-A76, 8 GB, Debian 13 (Linux 6.18.60). No SHA3 or DIT.
  • Fixed 1.5 GHz clock, passively cooled (nominal maximum 2.4 GHz; see the next slide)
  • taskset -c 3; rustc 1.98.1

Apple M1 Pro

  • 8P + 2E, 32 GB, macOS 14.0. Has SHA3 and DIT.
  • Shared with the owner's desktop and other agents' builds, at load 4–214. Medians are noisy, so only large effects are used.
  • No core pinning on macOS; rustc 1.98.1

Protocol

  • A shared bench lock is held for each round; the load is logged for each variant.
  • Interleaved variants with the order rotated. Criterion slope or mean. Medians of 3 (PR #33) or 5–8 rounds, with the spread reported.
  • Same binary where possible (--cfg rind_cpu_disable plus env toggles). aws-lc-rs or RustCrypto in the same binary is the drift control.
Constant-time checks run alongside the timings: admin/ct-vartime (disassembly scan), admin/ct-qemu (instruction traces under qemu-user), ctgrind (valgrind memcheck), and BINSEC (symbolic). They are run on the Pi and on the box under aarch64 emulation.

Hardware and method · Pi 5 clock

Why the Pi 5 runs at 1.5 GHz

The test board has no fan. At its full 2.4 GHz it overheats and slows itself down, so its CPU is held at a fixed 1.5 GHz.

The constraint

  • The board has no active cooling (no fan).
  • Short 2.4 GHz bursts push the SoC into thermal throttling.
  • Even at 1.5 GHz, the SoC runs at about 72–81 °C under light load.

The setting

  • A boot-time setting caps the CPU on purpose: scaling_max_freq = 1500000 (1.5 GHz).
  • The nominal maximum is 2.4 GHz. The governor is ondemand.
  • A sustained 2.4 GHz run without a fan would mostly measure throttling, not the code.

What it means for the numbers

  • All Pi 5 figures in this deck were taken at a fixed 1.5 GHz.
  • Both sides of every A/B ran at the same clock, so the ratios hold.
  • Absolute times are longer (performance is lower) than an actively cooled Pi 5 at 2.4 GHz would show.
Next step: rerun the key A/Bs at 2.4 GHz with active cooling to get stock-clock absolute times. The capped figures stay valid as relative comparisons. On Nov 13 the full suite ran on this board at 1.5 GHz, up to 75 °C, with no live throttling in 5 rounds. A second Pi 5 running the same suite at 2.4 GHz shows times 1.60× shorter with the same ratios (provisional, 3 of 5 rounds).

Phase 3 · Argon2id NEON fill (M1 Pro, 2026-11-11)

Fusing loads and stores into the rounds, then adding SHA3 xar, put the M1 Pro ahead of RustCrypto

perf/argon2-neon adds Argon2id and SIMD fills (AVX2, SSSE3, NEON). On the M1 the first NEON permutation lost to RustCrypto's portable code.

M1 Pro criterion medians, relative to the branch start (lower is better)
  • 705167ac: borrow the input blocks in place, instead of two 1 KiB memcpys per block
  • bd907631: fuse loads and stores into the rounds; one uzp1 per pair instead of an xtn per vector. 1 MiB: 1.018 → 0.800 ms.
  • 4ad61ae3: SHA3 xar does XOR and rotate in one instruction. The fill is built twice (NEON and SHA3) and selected at run time. SHA3 1 MiB: 0.724 ms.
  • Against the branch start (1.106 / 6.353 / 32.00 ms), the SHA3 fill takes 35%, 38% and 30% less time.
  • The open question going into Phase 4: the A76 has no SHA3, and its NEON fill still trailed RustCrypto.

Phase 4 · BlaMka with umlal

umlal is 13% faster on the M1 Pro and 2% slower on the A76, so it ships only in the SHA3 fill

BlaMka becomes (x + xy) + (y + xy): one umlal/umlal2 into each input, written as a single asm! block. Intrinsics did not work because LLVM folds them back to umull plus adds.

Phase 5a · PMU diagnosis on the A76

The PMU shows the cause: 68% of rind's cycles were back-end stalls on serial BLAKE2 dependency chains

rind ran 35% fewer instructions than RustCrypto at little more than half the IPC. It was latency-bound, not throughput-bound.

Cycles per 1 KiB block (1 MiB, 3 passes), median of 8 alternations
stall_backendother cycles
  • One BLAKE2 round is a single dependency chain only two vectors wide: 2-cycle ASIMD adds and 4-cycle umull.
  • The A76's 128-entry ROB cannot reach the next round, which is about 150 instructions away. RustCrypto's scalar code keeps four independent G chains busy on three integer ALUs.
  • Front-end stalls (≈1 per block) and cache refills were negligible, so memory and decode were not the problem.

Phase 5b · the fix: run two rounds at once

Running two rounds at once cuts Argon2id time on the Pi 5 by 27–34%, putting rind 23–26% ahead of RustCrypto

Each pass now runs rounds 2k and 2k+1 step by step in 16 vector registers with no spills. round! is a macro, because as a function LLVM kept it out of line.
