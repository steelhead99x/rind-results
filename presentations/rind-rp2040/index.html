The board

Two RP2040 boards: the first was backed up and left alone, and the runs used a Raspberry Pi Pico, backed up first

The chip

  • The RP2040 is the chip on the Raspberry Pi Pico. The first board's chip is silicon revision .
  • Rust calls this target thumbv6m-none-eabi: the ARMv6-M instruction set, with no operating system underneath.
  • Code runs from the MiB external flash (XIP, "execute in place") or from on-chip SRAM.

What was done to the boards

  • First board: an Arduino (Mbed OS) sketch of about KiB. Flash read times with picotool , all copies matched, never written.
  • Run board: a running . Its full 2 MiB was read times before anything was flashed; the copies are identical.
  • Neither backup is in this repository. Restoring the Pico is one picotool load.
The target survey lists the RP2040 as "the floor" of its suggested benchmark chips.

First error
error[E0463]: can't find crate for `std`

rind had no #![no_std], so the compiler looked for the standard library (std), which this target does not have. Without the custom-backend option, getrandom 0.4.3 fails first with "target is not supported".

Command: cargo build -p rind --release --target thumbv6m-none-eabi with --cfg getrandom_backend="custom", rustc .

Update, 2026-11-12: upstream rind at c333c59e gave 1,739 errors with rustc 1.98.1, and a std / alloc feature split takes that to 0 (slide 15).

The fixes

Patches 0003 and 0005 remove rind's need for std and CAS, and the images use a placeholder random source

patch 0003

no_std on bare metal

  • rind builds as no_std when target_os = "none", that is, with no operating system.
  • On Arm M-profile chips (Arm's microcontroller cores) it uses the portable backend.
patch 0005

ReuseCache without CAS

  • ReuseCache used compare-and-swap. On targets where target_has_atomic = "ptr" is not set, the same state machine now runs in a Cell.
  • No new dependency. This matches rind's existing assumption of one execution context on bare metal; a critical-section or portable-atomic crate would have added a dependency without changing that.
getrandom

Custom backend, not real entropy

  • The chip has no hardware random number generator, so the bench images plug a seeded SplitMix64 generator into getrandom's custom-backend hook.
  • It is not a source of entropy.
rind itself takes no position on randomness: the program that uses it supplies getrandom's backend. The RP2040's ring-oscillator bit is not a vetted source.

Where it stands

The 12 bench images were rebuilt with a timer fix and run on a Raspberry Pi Pico, with no known-answer failures

The SysTick-fixed images (one per bench file)

Each image is loaded over USB with picotool load (a 1200-baud touch on the serial port puts the chip in BOOTSEL mode), and results come back over USB serial as JSON.

  • Libraries in the images: rind, RustCrypto, dalek, libcrux. ring is left out (its Arm assembly uses NEON), and so is aws-lc-rs (it needs an OS).
  • Known-answer checks run before the timed rows. All runs in the snapshot report 0 failures.
  • Variant images, each changing one thing: sha512, ghash, opt (the final cfg), probe and padded builds (code-placement controls), p256mul (queued).
  • The images built before the timer fix are not used for results: their timer is wrong (slide 8).

The bug

  • SysTick is a 24-bit counter at the core clock, so it wraps about every 134 ms. The harness extends it to 32 bits in software.
  • The wrap handler never cleared SysTick's COUNTFLAG, so a sample that spanned a wrap gained (224) cycles.
  • The two SHA-512 numbers differ by 16.78 M cycles, the size of one wrap.

The fix and how it was checked

  • Fixed on harness branch , since pushed as ().
  • Checked on the board: the boot cross-check now agrees with the 1 MHz timer at about 125 cycles per µs, and the outliers are gone.
  • Every number in this deck comes from images built after the fix. The SysTick deck (presentations/rind-systick) covers the timer in detail.
The images built before the fix are not re-run. Their numbers are kept only as evidence of the bug, never as results.

How it was measured

Every row is timed in CPU cycles with SysTick, and each number is the median of per-round medians

Two clocks, because the M0+ has no cycle counter

The M0+ has no DWT cycle counter. The 1 MHz timer is read as RAWH, RAWL, RAWH, repeating if the high half changed, to avoid a torn read.

    What makes a comparison fair

    Finding 1 · SHA-512

    SHA-512 ran at about 2,200 cycles per byte in every library, because its unrolled code is bigger than the 16 KB flash cache

    Compression-function size vs the RP2040's 16,384-byte XIP cache

    At 16 KiB, rind went from to cycles per byte; libcrux stays at and rind's SHA-256 runs at . Estimate, not measured: refetching about 80 cycles per 8-byte QSPI line gives about 276k cycles per 128-byte block, which matches.

    rind, SysTick-fixed image → rolled SHA-512 image (cycles, 3 of 3 rounds)

    The rolled loop replaces HACL*'s SHA-512 only on Arm without CAS (ARMv6-M), where it is 1,724 bytes. Every index and branch depends only on the round number. A test checks it against the backend's own SHA-512 over 1 to 9 blocks.

    Side effect seen in the same images: code placement

    A probe image with the old code but memcpy moved to the new address reproduces the SHA-256 and HMAC rows, so those are placement, not the SHA-512 change. The HKDF row is not reproduced yet.

    Finding 2 · AES-GCM

    rind's AES-GCM ran 2.1 to 2.3× RustCrypto's time on long messages, because GHASH called __aeabi_lmul for every 64-bit product

    rind AES-GCM, SysTick-fixed image → muls-only GHASH image (cycles, 3 of 3 rounds)
    before:
    B · lmul calls
    after:
    B · lmul calls

    The change

    • The 32-bit GHASH took 32×32→64 multiplies per block. ARMv6-M has no umull, so each one was a call to __aeabi_lmul.
    • The new path uses 32-bit muls alone, as BearSSL's ghash_ctmul32 does: the high word comes from the bit-reversed operands. Its timing still does not depend on the key or the data.
    • Tested against the widening product on pseudo-random pairs and edge values.
    cfg bug, caught and fixed
    • The first gate was not(target_feature = "thumb2"). Stable Rust does not expose thumb2 on any Arm target, so it was also true on ARMv7 and thumbv7em.
    • Now all(target_arch = "arm", not(target_has_atomic = "ptr")): ARMv6-M plus tier-3 ARMv4T/ARMv5TE bare metal. The rebuilt aes_gcm and hmac code is byte-identical.

    Static scan of the M0+ images

    A scan of the built images ranks what is left: dalek's X25519/Ed25519 multiplies first, then P-256/P-384, then Poly1305

    lmul: static bl __aeabi_lmul call sites in the function. cond: conditional branches. * source count, no P-384 image. † public round and length loops, not secret data. All sizes fit the 16 KB cache; every hot symbol examined is in XIP flash, none in SRAM.

    Ranked candidates

    • 1. X25519 / Ed25519 (dalek u32): the most multiplies at run time, about lmul calls per X25519 (estimate). The code is in curve25519-dalek, not rind.
    • 2. P-256 / P-384 mul_add: in rind, already tested against fiat-crypto. Prototyped (slide 14).
    • 3. Poly1305: HACL* in libcrux, 52 lmul per update.

    Constant-time findings

    • Field multiply and square: no data-dependent branches or table lookups in the codegen. Lookup-table selects scan every entry.
    • libcrux P-256 point_add / point_double have 251 / 138 conditional branches: a concern in that comparison library, not in rind.
    • __aeabi_lmul itself: B, instructions, muls.

    Prototype · not timed yet

    A muls-only 32×32→64 helper removes every __aeabi_lmul from P‑256's field multiply and square, and passes 80 tests

    The change

    • On ARMv6-M, each 32×32→64 product in p256_mul32 and p384_mul32 is four 16-bit muls and adds. Arm cores with umull keep the widening multiply. Same cfg as the GHASH change.
    • In the P-256 bench image, mul_wide has muls and sqr_wide : and 0 lmul, the check required before timing.
    • P-384 mul_wide / sqr_wide also have 0 lmul in a release library build (576 / 300 muls).
