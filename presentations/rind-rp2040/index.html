The board

The test board is an RP2040; its firmware was backed up, and the first bench images have now been flashed

The chip

  • The RP2040 is the chip on the Raspberry Pi Pico. This one is silicon revision .
  • Rust calls this target thumbv6m-none-eabi: the ARMv6-M instruction set, with no operating system underneath.
  • Code runs from the MiB external flash (XIP, "execute in place") or from on-chip SRAM.

What was done to the board

  • On November 12 the notes recorded an Arduino (Mbed OS) sketch of about KiB. The full flash was read times with picotool ; all copies matched, and the flash had not been written yet.
  • Before the first bench flash, the board was running MicroPython. That firmware was saved and verified, then the twelve images were loaded with picotool. The backups are not in this repository.
The target survey lists the RP2040 as "the floor" of its suggested benchmark chips.

First error
error[E0463]: can't find crate for `std`

rind had no #![no_std], so the compiler looked for the standard library (std), which this target does not have. Without the custom-backend option, getrandom 0.4.3 fails first with "target is not supported".

The fixes

Patches 0003 and 0005 remove rind's need for std and CAS, and the images use a placeholder random source

patch 0003

no_std on bare metal

  • rind builds as no_std when target_os = "none", that is, with no operating system.
  • On Arm M-profile chips (Arm's microcontroller cores) it uses the portable backend.
patch 0005

ReuseCache without CAS

  • ReuseCache used compare-and-swap. On targets where target_has_atomic = "ptr" is not set, the same state machine now runs in a Cell.
  • No new dependency. This matches rind's existing assumption of one execution context on bare metal; a critical-section or portable-atomic crate would have added a dependency without changing that.
getrandom

Custom backend, not real entropy

  • The chip has no hardware random number generator, so the bench images plug a seeded SplitMix64 generator into getrandom's custom-backend hook.
  • It is not a source of entropy.
rind itself takes no position on randomness: the program that uses it supplies getrandom's backend. The RP2040's ring-oscillator bit is not a vetted source.

Where it stands

One command builds a firmware image for every benchmark; the first on-device run was on 12 November 2026

The UF2 images (one per bench file)

UF2 is the file you copy to the board: hold the BOOTSEL button, plug it in over USB, and copy the file across.

  • Libraries in the images: rind, RustCrypto, dalek, libcrux.
  • ring is left out. Its Arm assembly uses NEON (vpush) and does not assemble for ARMv6-M. aws-lc-rs is left out because it needs an OS.
  • Known-answer checks are built into the firmware and passed on all twelve images on the first flash.
  • The firmware lives in the public steelhead99x/rind-hardware repo. There is still no official QEMU machine with enough RAM, so those first-run numbers are not from an emulator.
The first runs found a SysTick wrap-count bug (fixed), SHA-512 at about 2,200 cycles/byte because HACL*'s unrolled loop missed the 16 KB XIP cache (patch 0006, 0.095× at 16 KiB), and AES-GCM at 2.1–2.3× RustCrypto from 32×32→64 helper calls (patch 0007, 0.48–0.53×). Details on slides 10 and 11.

    On-device runs

    The first flash is done; next is publishing the full results in rind-results, then restoring the saved firmware

    The firmware stack

    • cortex-m-rt provides startup code; embassy-rp (or rp2040-hal) drives the chip's peripherals.
    • Board needed: an RP2040 board with a 12 MHz crystal and W25Q080-compatible flash, like the official Pico.
    • Results come back over a USB serial port (USB CDC); defmt-rtt through a debug probe is the alternative.

    How results are measured

    Short operations are timed in CPU cycles, long ones with the 1 MHz timer, and every comparison runs the same way on the same chip

    Two clocks, because the M0+ has no cycle counter

    The M0+ has no DWT cycle counter, which the survey suggests using on the M33. The 1 MHz timer is read as RAWH, RAWL, RAWH, repeating if the high half changed, to avoid a torn read.

    On the board (rind-hardware a9d057a): SysTick is still extended to 32 bits, wrapping about every at 125 MHz. The first runs hit a COUNTFLAG double-count, which added 224 cycles to any sample that crossed a wrap. That is fixed, and the 1 MHz TIMERAW cross-check now lasts 300 ms: cycles against µs ( MHz).
