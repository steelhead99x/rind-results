The board

The test board is an RP2040, a small dual-core microcontroller, and its original firmware was saved before any work began

What the chip is

  • The RP2040 is the chip on the Raspberry Pi Pico. This one is silicon revision .
  • Cortex-M0+ is Arm's smallest 32-bit core. Rust calls this target thumbv6m-none-eabi: the ARMv6-M instruction set, with no operating system underneath.
  • Programs run straight from external flash (XIP, "execute in place") or from on-chip SRAM.

What was done to the board

  • It shipped with an Arduino (Mbed OS) sketch of about KiB.
  • The whole KiB flash was read times with picotool . All three copies matched.
  • The flash has not been written. The backup is kept outside this repository.
Why this chip: the target survey calls the RP2040 "the floor", the smallest and most limited chip in its suggested benchmark set. If rind runs here, larger microcontrollers are an easier step.

First error
error[E0463]: can't find crate for `std`

rind had no #![no_std], so the compiler went looking for the standard library, which does not exist for this target. Before that, getrandom 0.4.3 stops with "target is not supported" unless the build sets its custom-backend option.

The fixes

Two patches and a stand-in random number source make rind build for the RP2040 with no new dependency

patch 0003

no_std on bare metal

  • rind becomes #![no_std] when target_os = "none", using core and alloc instead of std.
  • On Arm M-profile chips (the microcontroller line) it uses the portable backend.
patch 0005

ReuseCache without CAS

  • ReuseCache used compare-and-swap. On targets where target_has_atomic = "ptr" is not set, the same state machine now runs in a Cell.
  • This matches rind's existing assumption of one execution context on bare metal. A critical-section or portable-atomic crate would have added a dependency without changing that, so neither was used.
getrandom

Custom backend, not real entropy

  • The chip has no hardware random number generator, so the bench images plug a seeded SplitMix64 generator into getrandom's custom-backend hook.
  • That is enough to run benchmarks. It is not a source of entropy and must not be used for real keys.
rind itself takes no position on randomness: the program that uses it supplies getrandom's backend. The RP2040's ring-oscillator bit is not a vetted source.

Where it stands

One command now builds a firmware image for every benchmark, and none of them has run on the chip yet

The UF2 images (one per bench file)

UF2 is the file format the RP2040's boot ROM accepts: hold the BOOTSEL button, plug in USB, and copy the file to the drive that appears.

  • Libraries in the images: rind, RustCrypto, dalek, libcrux.
  • ring is left out. Its Arm assembly uses NEON vector instructions (vpush), which ARMv6-M does not have. aws-lc-rs is left out because it needs an OS.
  • Known-answer checks are built into the firmware and will run on the first flash.
  • No official QEMU machine for the RP2040 can run these images, so only the build is published.

    Plan for on-device runs

    The next step is to flash the images, read results over USB, and put the original firmware back

    The firmware stack

    • cortex-m-rt provides startup code; embassy-rp (or rp2040-hal) drives the chip's peripherals.
    • Board needed: an RP2040 board with a 12 MHz crystal and W25Q080-compatible flash, like the official Pico.
    • Results come back over a USB serial port (USB CDC); defmt-rtt through a debug probe is the alternative.

    How we'll measure (plan, not results)

    Short operations are timed in CPU cycles, long ones with the 1 MHz timer, and every comparison runs the same way on the same chip

    Two clocks, because the M0+ has no cycle counter

    Larger Cortex-M cores have a DWT cycle counter; the M0+ does not. The 1 MHz timer is read as RAWH, RAWL, RAWH, repeating if the high half changed, to avoid a torn read.

    In the images built so far (commit 2cb88c3): SysTick is extended in software to 32 bits, wrapping about every at 125 MHz, and the 1 MHz TIMERAW timer is used only as a startup cross-check.
