ML-DSA signing · the idea

Most signing tries fail a check and start over, so the change runs the check that fails most often first

  • ML-DSA signs by trying, checking, and trying again. Most tries are rejected.
  • rind ran the rarely failing checks first, so a rejected try paid for work it did not need.
  • Now the low-bits check runs first, then z, then c·t0, the order mldsa-native uses. Each check is unchanged and constant-time.
  • An accepted try does the same work as before, so signatures are byte-identical. 3,000 signatures per set hashed the same before and after.

P-256 on x86_64 · where the time goes

Most of a P-256 key multiply is 37 point additions, and s2n-bignum's verified addition does them faster

One P-256 generator multiply, ns, 3 runs each (Sapphire Rapids, 2 vCPU KVM)
Partns
Whole multiply, before10,900 to 11,400
37 row selects2,270 to 2,420
37 additions, aws-lc's routine (before)7,500 to 9,100
37 additions, s2n-bignum p256_montjmixadd (after)5,700 to 7,000
Conversion back to affine1,500 to 1,800
Whole multiply, after9,300 to 9,650

What changed

  • The 37 window additions now use s2n-bignum's mixed addition, which has a HOL Light proof on every x86_64 OS. The aws-lc routine it replaces was proven on Linux only.
  • The old routine, its assembly files and two proofs are removed.
  • Three ideas to speed up the row select were measured and dropped: no gain, or under about 4%.

Portable big-number multiply · kixel-ai/rind#780

Computing four products before adding them cuts portable multiply time by 14–27% from 16 words up

Notes and limits

  • Each limb product used to wait on the carry chain before the next multiply started. Now four start at once.
  • This is the portable code that armv7 shares. x86_64 and aarch64 keep their assembly.
  • 2 words is slightly slower. No end-to-end RSA time is claimed for this change.
  • Ad hoc harness, Core Ultra 9 275HX pinned to one CPU, nine alternating samples, from fork head 7ebf1a90.

Generator tables on a cache line · kixel-ai/rind#790

Aligning the curve tables does not make code faster; it stops the linker from making it slower by chance

Raspberry Pi 5 at 1.5 GHz, P-256, 5 interleaved rounds
CaseTable offset beforeFix vs before
Table landed badly+8 bytes into a 64-byte lineremoves a 2.5–3.1% loss
Table already aligned well+321.000 on all four ops

The bad case was found when an unrelated branch moved the table and P-256 got 2.5–3.1% slower for no code reason.

What #790 does

  • One wrapper puts the P-256, P-384 and P-521 tables on a 64-byte boundary on every backend.
  • Table bytes do not change; at most 63 bytes of padding before each.
  • On x86_64, aligning alone measured no gain (steelhead99x/rind#79).
  • #790 was closed on 18 Nov without a merge. Its Criterion table compares rind with aws-lc-rs at one head, not the fix with its parent, so it is not shown here.
