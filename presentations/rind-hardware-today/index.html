Read it with these caveats

  • This compares rind against rind. It does not say rind now beats ring or RustCrypto.
  • Flagged on the ESP32-S3: libcrux also moved (32B open 0.497, seal 1.321) although its code did not change. The README puts this down to a layout shift in the 16 KB cache.
  • nRF52840 XChaCha 32B gains only 1.3% (0.987).
  • The patch is an optional set (patches/poly1305-32, five 26-bit limbs). The images were prebuilt and hash-checked at rind-hardware 7a14b38. No upstream PR has been opened.

Layout, not code

On the ESP32-S3, moving the same code to a new cache alignment moves short-input ratios by up to 0.7

Rowvspad0pad1031pad1039

pad0 is the published layout. pad1031 and pad2053 move every library by about 1 KB and 2 KB at the same alignment to the 32-byte line, and timed the same; pad1039 changes that alignment in seven of eight images.

Controls and caveats

  • A second pad0 run matched the published set: 0 of 558 rows moved. pad1039 moved 119 of 558.
  • No row crosses 1.0×: every verdict stays the same.
  • rind's SHA-256 64B cycles spread 26% over the three layouts. Whether the 16-byte fetch or the 32-byte line matters is not separated.
  • The 3-run interval in RESULTS.md covers run-to-run noise only. Read short-input ESP32-S3 ratios with this layout caveat.
  • The nRF52840 relinks moved no short-input ratio by more than 0.01.

What it means

  • ChaCha20-Poly1305 does not move: that gap is Poly1305 compute, which the patch on slide 3 addresses.
  • ring's and libcrux's X25519 and ring's P-256 speed up sharply (libcrux X25519 0.061×), so their published rows measure the 16 KB cache too.
  • Same findings as the earlier 40 MHz runs at rind 99b509a. No verdict flips.
  • 32 KB is a build option for this check only; the published numbers use ESP-IDF's 16 KB default.

Two harness fixes

The ESP32-S3 flash ran at 40 MHz instead of 80, and a leftover watchdog reset the nRF52840's first image

Flash clock, ESP32-S3

  • The build asked for 80 MHz, but espflash writes the clock into the image header, defaults to 40 MHz and does not read sdkconfig. Every published log said Boot SPI Speed : 40MHz.
  • Reflashing the same sha2.elf at 80 MHz: rows that stream code from flash ran in 0.520× the cycles (SHA-512: 1.54 M → 0.80 M cycles a block). ring and the hardware rows did not move.
  • So cache-missing rows were up to 1.92× too slow, and they were compared against cached rows at a bias.
  • Fix: flash with --flash-freq 80mhz, print the clock from the logs, fail a set that mixes clocks, rerun the set. The 40 MHz set is kept in results/diag/esp32s3-40mhz-2026-11-11/.

Watchdog, nRF52840 (T1000-E)

  • The first image flashed after Meshtastic reset 89 s into its run, after 128 results.
  • A probe read RUNSTATUS = 1 and CRV = 2,949,120 (90 s), then reset 89 s after its last feed: Meshtastic's watchdog survives a software reset and the bootloader.
  • Fix: the firmware records the watchdog state at boot and feeds every enabled reload register between timed regions. The poly1305-32 run fed it in every start record.
  • No published number changes: all of them are from complete runs.

RP2040 port · rind-bench → rind-hardware

The RP2040 images build and the firmware is now public as rind-hardware; first-run numbers are not on main

RP2040 (Cortex-M0+, 125 MHz)

  • All 12 bench images build for thumbv6m-none-eabi from rind 98568332 with patches 0001–0005: 0003 gives rind no_std, 0005 runs ReuseCache in a Cell where there is no compare-and-swap.
  • ring is left out (its Arm assembly does not assemble for ARMv6-M). getrandom is a seeded SplitMix64, not an entropy source.
  • Both main branches still say "not yet run on hardware". The SysTick wrap fix and patches 0006–0007 are on rind-hardware branches rp2040/systick-wrap-fix and rp2040/armv6m-sha512-ghash, not main, so their numbers are left off this deck.

The firmware repo move

  • steelhead99x/rind-bench is archived. Its history was squashed into the first commit of the public steelhead99x/rind-hardware, 8d9c1bb (12 Nov, 17:19 PST).
  • rind-results now points clone URLs, reproduce steps, the skill and the toolchain script at rind-hardware.
  • Provenance SHAs already published (for example rind-bench f656f95 for the RP2040 images) were left as recorded. They refer to the private history, which is not public.

Honesty check

What these numbers do not show: noise, layout, and work that is not yet on main

Noise and layout

  • Board results are 3 fresh boots per image. The low–high run medians bound the median with 75% probability and cover run-to-run noise only.
  • ESP32-S3 short-input rows depend on code layout by up to 0.7 (slide 4). The poly1305-32 A/B moved libcrux by layout alone.
  • The m1pro and pixel9pro host runs are marked noisy in the README; xeon-vm is a shared cloud VM.
  • The 32 KB cache runs are a diagnostic build, not the published configuration.

Not shown, or pending

  • RP2040 on-device numbers: on rind-hardware branches only.
  • Orin and today's Pi 5 lane: in progress.
  • poly1305-32 is not upstream: no PR or issue was opened.
  • Older provenance SHAs point into the private rind-bench history.
  • The RP2040 has no hardware RNG; its images use a seeded placeholder.
