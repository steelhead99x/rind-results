# ESP32-S3: why HMAC-SHA256 64B and HKDF expand moved at the repin

At rind 99b509a6 rind's hmac-sha256 64B took 3.61x ring's time and hkdf-sha256 expand 5.31x; at 98568332 they take 2.20x and 6.93x (`../esp32s3-99b509a-80mhz-2026-11-12/` against `results/`, both at 80 MHz flash). The answer: **layout, not a code change.**

1. **No code on the path changed.** `git diff 99b509a6 98568332` touches none of `rind/src/high/hmac.rs`, `hkdf.rs`, `hash.rs`, `digest.rs`, `rind/src/low/portable/sha.rs` or `low/generic/blockwise.rs`; its changes are Keccak, the P-256/P-384/P-521 field code, RSA, hash-to-curve and x86-64 assembly. The firmware's own `Cargo.lock` is unchanged (libcrux-sha2, ring and RustCrypto at the same versions), and so is the firmware but for the padding hook. In the two hmac images every rind HMAC/SHA-256 function and every libcrux-sha2 function has the same size (`nm -S`).
2. **The code moved.** Other rind code before it changed size, so rind's HMAC functions now sit 2,644 bytes closer to libcrux's `sha256_update` in the hmac image (`HmacKey<Sha256>::new` 11,132 bytes before it at 99b509a, 8,488 at 98568332), and 25,068 bytes closer in the hkdf image (171,216 and 146,148). libcrux's own code moved by only 16 bytes.
3. **With a 32 KB instruction cache both pins time the same.** `icache32/` is hmac, hkdf and sha2 built with `sdkconfig.icache32` at 98568332, three runs each at 80 MHz: rind hmac-sha256 64B 27,735 cycles (99b509a's `../hmac-icache32/`: 27,735), hkdf-sha256 expand 12,054 (12,060), sha256 64B 11,016 (11,014). There rind is the fastest at HMAC 64B (115.6 µs against ring's 140.3 µs) and within 2% of RustCrypto at HKDF expand (50.2 µs against 49.2 µs; ring 60.6 µs). The whole difference at 16 KB is cache misses.
4. **Where the time goes (PC samples).** `spin-hmac-64-rind.*` and `spin-hkdf-expand-rind.*`: rind-bench's `rng-diag` firmware with `RIND_BENCH_SPIN=hmac-64-rind` / `hkdf-expand-rind` calls the bench's rind operation in a loop on core 0 while a core-1 task samples the preempted PC every tick (400 samples; `*.functions.txt` is `addr2line -fC` against the spin image, `images.sha256` its hash). HMAC 64B: 206 samples in libcrux's `sha256_update`, 80 in the u32 rotates inlined into it, 26 in its big-endian loads, 25 in rind's own `sha256_compress_blocks` (the key's padded blocks), 28 in `HmacKey::new`, 25 in the tag copy. HKDF expand: 185 in `sha256_update`, 110 in its rotates, 35 each in rind's digest, HMAC streaming and `Prk` code. `sha256_update` alone is 12,611 bytes, three quarters of the 16 KB cache, so the misses on each call depend on which lines of the rest of the path share its cache sets: where the linker happens to put them.

The spin images are a different link from the bench images, so the samples say which code runs, not how many misses each bench image takes.

## A caveat on the relinked builds

The same symbol tables show what rind-bench's `--pad` relinks actually move. The padding static lands after the libraries' code (at 0x420871b8 in the sha2 image), not ahead of it as `pad.rs` claimed: from pad0 to pad1031 nearly every library function moves by 12 bytes (the hook's own code), and pad1031 and pad2053 lay out everything before the padding identically; what the padding moves is the code after it, mostly the firmware's own bench loop and harness. So `../esp32s3-relink-98568332/` measures three placements of the harness against the libraries, and a 12-byte shift of the libraries, not three placements of the libraries. That a 12-byte shift moved SHA-256 64B from 2.36x to 3.55x libcrux shows how sensitive these rows are; it doesn't cover the shifts of kilobytes that a repin causes, which is why these two rows moved further at the repin than in any relink.
